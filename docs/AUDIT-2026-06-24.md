# AUDIT d'écart - Blindify web vs Definition of Done

> Écrit le 2026-06-24. Audit en lecture seule, aucun code modifié, aucun build, aucun E2E lancé.
> Cible : les 4 points du Definition of Done (HANDOFF.md §7). Mesure l'écart, ne construit rien.

## Résumé en une ligne

Le cœur du jeu tourne. Sur les 4 points : aucun n'est bloqué côté serveur, 1 reste à prouver (8 joueurs), 1 n'existe pas (signalement bug), 1 est à reskin (logo), 1 demande une vraie passe (mobile). Aucun chantier ne touche la machine à états fragile si on reste discipliné.

---

## Point 1 - Deux modes principaux à 8 joueurs

**Verdict : techniquement permis, JAMAIS prouvé à 8.**

- Backend : cap à 16, défaut 12, plancher 2. `backend/src/controllers/roomsController.ts:147` (`min(max(n,2),16)`). 8 est largement dans la marge, aucun changement de cap nécessaire.
- Frontend friends : défaut 8 si `room.max_players` null, grille `sm:grid-cols-2`. Tient à 8. `frontend/src/app/multiplayer/FriendsLobbyView.tsx:327`.
- Event : pas de grille de slots (juste un compteur), aucun risque de layout.
- Classement / reveal : liste flex verticale, `max-width:460px`, scale sans casser à 8. `TheaterGameView.tsx` (finale-board).

**L'écart est de la PREUVE, pas du code.** Les E2E montent à 2 joueurs max (`multiplayer-2players`, `event-2players`, `multiplayer-full-game`, `multiplayer-sync`). Le seuil de 8 et la perf socket à 8 clients simultanés ne sont pas vérifiés.

**À faire** : valider une vraie partie à 8 (les deux modes) + un E2E qui monte à 8. Effort faible-moyen, gros gain de confiance.

## Point 2 - Canal de signalement de bug in-app

**Verdict : n'existe pas. Confirmé.**

- Aucun composant frontend (modal/bouton "signaler/feedback/bug/support").
- Aucune route backend (`routes/` : auth, games, likes, rooms, stats, audioSources, friends, invitations, import, quickPlay, challenges. Pas de feedback).
- Aucune table DB (`schema.sql`, migrations : rien pour feedback/bug).
- Aucune lib email côté blindify (pas de Resend/nodemailer dans `backend/package.json`).

**Briques déjà là pour le construire** :
- Sentry : placeholder `SENTRY_DSN` dans `.env.example:29`, non câblé (capture passive, pas un canal joueur).
- Pattern réutilisable sur le VPS : `/opt/clearpath-feedback` (Resend + table `feedback_responses` + route `/api/feedback`).
- Postgres opérationnel : ajouter une table `bug_reports` est trivial.

**À faire** : construire le canal. Décision de forme requise (voir Décisions). Effort faible-moyen, self-contained, risque bas.

**Verdict : un logo existe mais ne colle pas à la DA. À reskin.**

- Surfaces mortes qui l'affichent encore :

  - `app/auth/login/page.tsx` : auth abandonnée (remplacée par le wizard nom+musique).
- Surfaces vivantes OK (conversion analog en cours) : `landing/navigation.tsx`, `stats/page.tsx`.

**À faire** : un logo qui respecte la DA actuelle (probablement reskin de l'image + fix du composant + retrait des surfaces mortes), pas un from scratch. Périmètre à confirmer (voir Décisions). Risque technique bas.

## Point 4 - App adaptée au téléphone

**Verdict : pas fini. Plusieurs correctifs ciblés, surtout sur l'écran de jeu mobile (`TheaterGameView.tsx`).**

Faux positif écarté : le `<meta viewport>` EST présent dans le HTML de prod (Next.js l'injecte, vérifié dans `out/index.html`). Ce n'est pas un problème.

Problèmes réels prouvés dans le code (à confirmer sur device réel, l'analyse est statique) :

1. **Grille de jeu à colonne fixe.** `TheaterGameView.tsx:182` : `gridTemplateColumns: "1fr 320px"` sans breakpoint propre. La correction mobile est à `@media (max-width:900px)`, pas alignée sur 640px. Risque : à 375px le classement latéral écrase la zone de jeu si la media query ne mord pas comme prévu.
2. **Drawer de chat fixe 340px.** `TheaterGameView.tsx:1141` : `position:fixed; width:340px`. Sur 375px, chat ouvert = jeu quasi inaccessible. Pas de passage plein largeur sur mobile.
3. **Cibles tactiles du picker "Qui a ajouté" trop petites.** `TheaterGameView.tsx:1017` : avatars 26px, hauteur de bouton ~20-24px, bien sous les 44px requis. Erreurs de sélection au pouce probables.
4. **Breakpoints désynchronisés** (640px vs 900px) : états intermédiaires (tablette portrait, chat ouvert) mal gérés.

Plus léger : QR fixe 168px en event (tient mais serré), quelques `text-[9px]/[10px]` sur labels, `whitespace-nowrap` sur noms longs (masqué par overflow-hidden, pas de scroll horizontal réel).

**À faire** : passe mobile sur le parcours des 2 modes (wizard -> lobby -> jeu -> reveal -> résultats). C'est le plus gros morceau et le plus proche de l'usage réel. Tout changement sur `TheaterGameView`/`MultiplayerGameClient` exige un E2E 2 joueurs derrière (zone fragile, cf. PITFALLS §2).

## Filet de sécurité E2E - résultat (2026-06-24)

E2E `multiplayer-2players.spec.ts` lancé sur la prod : **1 passé / 1 ÉCHOUÉ**.

- Test KO : "full game: launch, play 2 rounds, verify round advancement". Après le clic "Lancer", l'UI de jeu (`.theater-round`) n'apparaît jamais.
- Cause localisée via logs serveur : le `POST /blindify/api/rooms/<code>/start` renvoie **400** (rejeté par le backend). Du coup aucun round ne démarre, aucun `.theater-round` rendu.
- Gardes 400 candidates dans `roomsController.startGame` : "playlist_provider_invalid" / "provider_connection_missing" ("Connexion Spotify requise"). Le host du test importe via un profil Spotify SYNTHÉTIQUE (`open.spotify.com/user/yigiha...`) sans connexion OAuth réelle.
- **PAS causé par le renommage + fix tests audio** (qui ne touchent ni le launch ni la boucle de jeu). Condition préexistante, héritée du lot QoL de la session précédente jamais retesté.

**Ambiguïté NON tranchée** : artefact de test (compte synthétique) VS vrai bug. Risque réel : avec le nouveau wizard, un vrai user colle un lien de profil Spotify ; s'il faut une connexion OAuth pour démarrer, il prend le même 400. À CONFIRMER par une vraie partie 2 joueurs (compte réel / depuis le téléphone), impossible à reproduire en headless avec audio.

**Reco** : confirmer la santé réelle de la prod (vraie partie) AVANT tout chantier mobile/8 joueurs, qui dépendent d'une boucle de jeu saine. Si bug réel sur le start avec profil collé -> priorité 1, à investiguer sur un build dev instrumenté (pas en aveugle sur la prod).

### Résolution (2026-06-24, même jour)

**Tranché : ARTEFACT DE TEST, pas un bug prod.** Preuves DB :
- Users de test (GameHost 2272, Player2 2273) : **0 piste** dans `audio_sources`.
- Global prod : **4529 sources réparties sur 15 users réels**. Base saine.
- Le 400 = garde `need_more_music` (`roomsController.ts:619`, "Il faut au moins 2 joueurs ayant importé leur musique"). Le test importe un profil Spotify synthétique (0 piste, OAuth requis) et Player2 n'importe rien -> moins de 2 joueurs avec musique -> refus légitime.

**Conséquence** : le E2E `multiplayer-2players` meurt à la précondition musique, donc il **ne teste jamais la vraie boucle de jeu** (launch -> rounds -> reveal). Ce n'est pas un filet de sécurité utile en l'état.

**À faire pour en faire un vrai filet** : seed de vraies pistes jouables (Deezer, pas d'OAuth) pour les 2 users de test avant le launch, OU import réel via le flux Deezer. Ensuite le test exerce vraiment la boucle. Tant que ce n'est pas fait, on n'a pas de validation E2E automatique de la boucle de jeu.
